# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Integrative Transcriptomics Viewer (ITV) is a Python package (import name
`integrative_transcriptomics_viewer`) forked from `genomeview`, specialized for viewing
long-read RNA-seq data in transcriptome context inside Jupyter notebooks. Output is SVG,
rasterized to PNG/PDF/HTML as needed.

## Environment / install

Requires conda; there is no plain `pip install -r requirements.txt` path checked into git
(`requirements.txt` is generated, not committed).

```bash
make install       # creates/reuses a conda env named itv-<version> (from __init__.py __version__) and pip installs the package
make devinstall     # same, but editable install (`pip install -e .`)
make update         # reinstall into the existing versioned env
make clean          # removes the itv-<version> conda env
conda activate itv-<version>
```

`environment.yml` is generated by `generate_env_yml.py` (reads `__version__` from
`src/integrative_transcriptomics_viewer/__init__.py` to name the env `itv-<version>`) — it is
regenerated automatically by `make create-versioned-env`, don't hand-edit it expecting it to stick.

There is no test suite in this repo. Verify changes by exercising the notebooks in `examples/`
(`examples/demo-ITV.ipynb` is the canonical tutorial/vignette) and checking rendered SVG/PNG
output, not by running `pytest`.

Linting is configured via `ruff` in `pyproject.toml` (`select = ["E", "F", "I", "A"]`,
`ignore = ["E501"]`), scoped to `src`.

## Building docs

Sphinx docs live in `docs/` (theme: pydata-sphinx-theme) and are built on Read the Docs per
`.readthedocs.yaml`. Locally: `cd docs && make html`. `docs/requirements.txt` covers the doc
build's own deps.

## Architecture

### Rendering pipeline (bottom layer, rarely touched)

- `genomeview.py` — `Document` (top-level SVG canvas; holds `ViewRow`s, drives layout/render
  and Jupyter `_repr_html_`/`_repr_svg__`), `ViewRow` (horizontal row of `GenomeView`s), the base
  `GenomeView` (one genomic window; owns a `Scale` and a stack of `Track`s), and `Scale`
  (genomic-coordinate ↔ pixel-coordinate mapping plus reference-sequence lookup).
- `track.py` — base `Track` interface: every visual element implements `layout(scale)` then
  `render(renderer)` (a generator yielding SVG-producing renderer calls). Concrete tracks:
  `axis.py` (`Axis`), `intervaltrack.py` (`IntervalTrack`/`Interval`, base for feature tracks),
  `bedtrack.py` (`BEDTrack`, `VirtualBEDTrack`, BED12/tabix/bigbed fetch), `bamtrack.py`
  (`SingleEndBAMTrack`, `PairedEndBAMTrack`, `GroupedBAMTrack`, `BAMCoverageTrack`, `VirtualBAM`
  for merging/aggregating reads), `graphtrack.py` (`GraphTrack`, `BigWigTrack`).
- `svg.py` — `SVG`/`GraphicsBackend` (low-level SVG primitive emitters) and `Renderer`
  (coordinate-offsetting wrapper passed down through the layout tree so nested elements draw in
  local coordinates).
- `export.py` — `save()` is the public entry point for writing a `Document` to
  `.svg`/`.png`/`.pdf`/`.html`; it shells out to one of several converters (`resvg`, `cairosvg`,
  `rsvg-convert`/librsvg, Inkscape, or webkitToPDF for PDF) — see `_getExportConverter` and the
  `_check*` probing functions. `SvgSplitter` tiles very tall/wide SVGs into multiple raster
  images (SVG/cairo rasterizers choke past certain dimensions).

### Public/high-level API (what users and most changes touch)

- `convenience.py` — the `Configuration` class is the main user-facing entry point. It indexes a
  GTF (gene/transcript/exon ID and name lookups) and holds BED annotation sources, then exposes
  `plot_*` methods (`plot_feature(s)`, `plot_interval(s)`, `plot_read(s)`, `plot_exons`,
  `plot_splice_junctions`, `plot_by_features_as_tab`, `plot_by_classification_over_features`,
  `plot_by_classification_as_tabs`, …) that build up a `Document`/`ViewRow`/`GenomeView`/track
  stack for you from just a feature ID/name and a dict of BAMs. Almost all of these forward
  `**kwargs` down to the private `_build_view_row`, which does the actual track assembly.
- `classification.py` / `cellbarcode.py` — pluggable strategies (`Classification`,
  `CellBarcode` ABCs and concrete implementations) for grouping/labeling reads, e.g. by IsoQuant
  output or BAM tags, or for parsing single-cell barcodes (Haas-style, ONT, "standard").
  `Configuration.plot_by_classification_*` methods consume these.
- `annotation_matching.py` — matching feature annotations by substring (`IsoquantSubstringAnnotationMatching`).
- `quickconsensus.py`, `bam_read_operations.py` — read-level helpers (consensus/SNP handling,
  CIGAR/clipping utilities) used by the BAM tracks.
- `utilities.py` — misc helpers (`get_one_track`, chrom-name normalization, reservoir sampling
  for downsampling reads, gzip-aware file opening).

### The kwargs signature/doc synchronization system (unusual — read before editing `Configuration`)

Because most `plot_*` methods only declare `**kwargs` and silently forward to
`_build_view_row`, IDEs/Jupyter can't autocomplete or introspect their real accepted options.
This is solved at **import time** by a generated block at the bottom of `convenience.py`,
delimited by `# === ITV OPTIONS SPEC: begin/end ===`:

- `BuildViewRowOptions` is a frozen dataclass that is the **authoritative spec** of every keyword
  `_build_view_row` accepts, each field carrying a `metadata["doc"]` description.
- `_itv__compute_option_exclusions()` statically analyzes (via `ast`) which of those kwargs each
  `Configuration` method actually consumes/forwards, so a method isn't advertised as accepting
  options it silently drops.
- `_itv__augment_docs_from_spec()` appends an "Other Parameters" section to each `plot_*`
  method's docstring at import time.
- `_itv__install_signatures_from_spec()` rewrites `func.__signature__` on every `Configuration`
  method that has a `**kwargs` catch-all, so `help()`/Jupyter tab-completion show the real
  parameter list.

**If you add, rename, or remove a keyword argument on `_build_view_row` (or change which
`plot_*` method forwards which kwargs), update the `BuildViewRowOptions` dataclass fields to
match** — the spec is hand-maintained, not derived from `_build_view_row`'s signature (only
defaults/annotations are pulled from the live signature where present).

After changing `Configuration`'s public methods or `BuildViewRowOptions`, regenerate the type
stub (do not hand-edit `convenience.pyi`, which is marked "Auto-generated ... do not edit by
hand"):

```bash
python tools/generate_convenience_stub.py
```

This script stubs out optional heavy dependencies (`cairosvg`, `ipywidgets`, `intervaltree`) so
it can import `convenience.py` and introspect signatures without a full environment.

### Docs structure

`docs/convenience_configuration/` has one `.rst` page per major `Configuration` method, included
from `docs/convenience_configuration.rst`; keep these in sync with method names/signatures when
adding or renaming `plot_*` methods.
